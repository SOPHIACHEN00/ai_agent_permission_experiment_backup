## 下一步真正要回答的研究问题

在相同任务、planner trace 与合成初始状态下，动态权限策略是否比静态策略更好地兼顾：

1. **效率**：任务 oracle 成功率、授权请求/用户打扰次数、完成所需步骤及时间；
2. **隐私**：实际读取的记录与字段、实际发出的字段与接收者，以及任务不需要却被授权或访问的范围；
3. **安全守卫**：越权尝试数、在工具执行前被阻断的比例、撤销/一次性授权是否严格生效。

不要把这些压成一个未经解释的「privacy score」。建议至少分别报告“获准范围”和“实际访问/发送”，以区分过宽授权与已经发生的数据暴露；记录 ID 及搜索结果也要考虑在暴露口径里。

## 建议的最小对照设计（尚未实施）

先选几条能有明确任务 oracle 的多轮任务，冻结 planner 轨迹及 mock 初始状态。**策略比较**保留 ledger 和 monitor 不变，只改变权限策略，例如静态宽授权、静态窄授权、当前 RL 策略；这样差异才主要来自权限决策。每个 arm 使用相同任务实例、用户反馈脚本、随机种子与工具结果。

**组件消融**另开合成诊断：分别去掉 ledger 的持久生命周期约束或绕开 monitor 的执行前检查，观察一次性授权/撤销/范围检查是否失效。这不是安全部署方案，不能接真实工具；仅用于归因机制作用。当前仓库里的六项测试**还不是这些消融实验**。
